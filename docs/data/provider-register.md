# Provider capability register

Primary product and policy pages were checked on 11 November 2026. The register covers products Anchor Buddy can route or prepare and explicitly identifies pending capabilities. Service configuration, data rights, current response status and reviewed analytical coverage have separate fields.

The report preserves the original provider IDs and the legacy `providers` array. `capabilities.schemaVersion` is 2. Stable product IDs distinguish products that share an adapter. Product roles reuse the V2 evidence roles. Place results, active warnings, tariff estimates and an assistant have their own context roles because they do not establish any of the seven analytical layers.

## Public response

`GET /v1/providers` returns `{ providers, capabilities: { schemaVersion: 2, products } }`. Existing clients can continue to read `providers`. Its legacy `offline.allowed` is false when a blanket offline permission cannot be established.

Optional decimal `latitude`, `longitude` and `radiusNm` resolve routing for an area. Coordinates are WGS84 and latitude is within ±85°. Both coordinates are required when an area is supplied. Radius is 0.25–25 nautical miles and defaults to 0.25 when omitted. Invalid input returns `400 INVALID_PROVIDER_AREA`. The request performs zero upstream calls and the response omits the supplied coordinates.

For Split with default development settings, `met-locationforecast-wind` and `osm-overpass-europe` are `available` with `statusBasis: "configuration"`. `met-oceanforecast-waves` is `not-covered` with `statusBasis: "routing"`, and `open-meteo-marine-waves` is `disabled`. In Singapore, both EMODnet products resolve to `not-covered` before transport. An existing product-level observation can resolve to `partial` or `unavailable` with `statusBasis: "response"`. Discovery results and source dates stay on `/v1/regions/discover`.

`routing: "eligible"` describes the request extent. `"not-selected"` identifies global Overpass when the complete disk takes the Europe route. `"requires-review"` identifies products that need a reviewed region or mapping. `"unchecked"` is used without an area or where geography does not apply. The resolver checks activation and routing before accepting an observed product status. Analytical use requires appropriate rights, evidence role, reviewed geometry, current evidence and the existing release gates.

Authentication exposes the mode and optional credential state `configured` or `missing`. Public URLs come from checked-in primary references. Endpoint overrides, API keys, entitlement identifiers, reviewer identities and contacts are omitted.

## Registering and rechecking products

Add the stable provider ID to the legacy array when needed and give each product a unique ID. Link it to the actual adapter or mark it pending. Record public source and primary policy pages, attribution, routing limits and original verification date. Add each right separately using its primary policy and UTC verification date. Keep `unknown` where source terms, account entitlements, originator restrictions or analytical use remain unresolved.

Recheck sources before enabling a new endpoint, moving a product to another deployment, distributing a new pack, or when terms or service modes change. Update verification dates after reviewing the actual terms. Operators can record a re-verification deadline in their deployment policy and return affected rights to `unknown` when that deadline is missed. A rights review does not renew a cached observation, forecast, pack or maritime attestation.
