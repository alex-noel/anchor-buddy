## Compatibility and activation

`schemaVersion` is an integer major version, separate from an immutable content `version` string. Absent `RegionPack.schemaVersion` means legacy 1. Explicit 1 remains supported. Unknown versions return `unsupported-version` with recovery instructions before a caller writes or activates anything. Local v2 envelopes require exactly 2; they do not silently wrap future records as legacy data.

V2 is an **exchange and migration contract**. The existing engine does not consume composed v2 packs yet. `validateRegionPack`/`validateLiveRegionPack` explicitly reject all v2 packs, any pack carrying `snapshot`, and any source carrying a v2 `evidence` envelope until DATA-03's reviewed composition adapter is integrated. SAFE-01 now validates source primitives and assesses known intersections conservatively; every primitive-bearing pack retains `hazard_model_review_required` and insufficient hazard coverage until a genuine version-bound model review is integrated. Unknown extent or uncertainty remains unknown. Do not strip version/snapshot/primitive fields to bypass a gate. These are additive declarations, not permission to downgrade a v2 payload to v1. Missing hazards cannot become complete coverage.

The analytical component-to-layer mapping is fixed: `static-analysis` → bathymetry/hazards; `rules-habitat` → restrictions/habitat; `weather-current` → weather/currents; `water-level` → tides. Display and places/tariffs components establish none of these seven layers. DATA-04 current products use weather-current components; astronomical tide never supplies currents. Coverage review validity must span the entire coverage interval, not only the assessment instant.

Standalone `validateSnapshotIdentity` checks structure, independently observed hashes and exact review bindings. Its success is **not** a release approval. The caller must hash actual immutable bytes, check byte count, parse those exact checked bytes, resolve all source/coverage IDs, validate layer applicability and satisfy every existing API release gate (maritime, coverage, geometry, station mappings, on-water). It must not copy claimed hashes from a manifest into the observed-hash map. Inherited object keys cannot satisfy observed hashes. DATA-03 owns byte verification/composition; API/mobile integration retains the existing staged/atomic activation checks. No cryptographic signing or reviewer authentication system is claimed here.

## Coordinates, units, time and display

Positions are WGS84 `[longitude, latitude]`, longitude degrees ±180 and supported analysis latitude ±85. Native watch deliberately retains its separate named-coordinate protocol and ±90 validation; this contract does not change it. Analysis geometry is original unsimplified geometry, including holes. Display tiles, point forecasts, scientific DTM samples and seabed context cannot assert analytical coverage. Bounding rectangles used for routing are not reviewed coverage polygons.

Lengths/depths/uncertainty are metres, displacement kilograms, wind/current speed knots, bearings true degrees, with no datum implied by a number. Preserve source units/datum separately; unknown conversion relationships remain unknown. Instants in new envelopes are UTC ISO strings ending `Z`. Legacy explicit-offset timestamps remain readable and are not reformatted by migration. Calculation intervals are half-open `[from, until)`; a forecast ending at departure covers that boundary but not time after it. Business tariff dates/times use the declared IANA timezone, independently of the user's display zone. Source refresh, retries, cache reads and composition never advance source issue, survey or retrieval dates.

Exact conversion definitions: 1 foot = 0.3048 m; 1 nautical mile = 1852 m; 1 statute mile = 1609.344 m; 1 knot = 1 nautical mile/hour. Thus ft/m = `1/0.3048`, mi/nm and mph/knots = `1852/1609.344`, km/nm and km/h/knots = `1.852`. Untouched drafts retain their exact canonical stored number. Edited numbers convert directly from the declared unit, with no intermediate rounding. UI arithmetic assertions use `max(1e-9, abs(expected)*1e-12)` in canonical units. **This tolerance never changes a safety threshold or geometry outcome.**

Display formatting may round (existing inputs two displayed decimals; depth/distance usually one), but must not write display-rounding results back into unchanged canonical data. Existing form helper `parseUnitDraft` supports the exact ratio contract; APP-02/APP-07 must replace approximate imperial ratios at its call sites (`3.28084`, `1.15078`) when wiring edited-unit compliance. FOUNDATION-02's tests exercise untouched and edited drafts with exact factors; they do not certify every current UI call site.

## Fingerprints, persistence and migration hooks

SAFE-02 owns the canonical compatibility fingerprint implementation. The relevant fields are vessel type, length/beam/loaded draft/displacement/air draft (missing distinctly represented), anchor manufacturer/model/rode configuration IDs, anchor type, rode type, usable length and bow height. Serialize a fixed named-key object using canonical JSON (lexicographically sorted keys, original finite JSON numbers, no display rounding; absent explicitly null where specified), UTF-8, SHA-256 lowercase hex. Units/language/name/UI selection are not compatibility inputs. New equipment-identification fields belong to SAFE-02's separately integrated model; no user assertion grants a rating.

`readLocalRecord` checks supported version/identity before the owner's payload validator. Payload validation exceptions become `invalid`; malformed migrations never call storage. `commitMigratedRecord` awaits an injected atomic complete-record commit and returns `committed` only after success. Failure returns the original input for recovery and a nonsecret error. It does not itself implement transactions, delete legacy keys, update active state, repair invalid numbers, or call native watch. APP-02 supplies an atomic SQLite/web implementation; one localStorage JSON replacement is atomic, multiple key writes are not.

The existing seabed migration remains `getPreferredBeddings`: explicit multi-choice wins, empty is no preference, absent falls back to legacy single or `any`. Existing `readSavedSearches` hides unproven historical result values and marks reassessment required. Never restore hidden numbers from an older snapshot as active evidence. Migration preserves coordinates, canonical dimensions, original money numbers/decimal strings, currency and source dates; adding an envelope is not permission to recalculate them. Failed migration retains original bytes/keys. Validity/freshness is reassessed separately. APP-06 stores no trusted Assessment, monitoring flag, confirmed-anchor state, arrival acknowledgement or confirmed alarm radius. Resume must reset confirmations and explicitly reassess; it cannot issue a watch command.

## Tide semantics and original measurements

`minWaterLevelM` and `maxWaterLevelM` are nominal bounds in the target declared datum. A reviewed signed datum offset changes nominal values once. Source units/datum and transformation provenance remain with evidence. `uncertaintyM` is a separate nonnegative conservative bound; unknown contributions yield null, never zero. DATA-04 retains source/conversion/weather-residual contributions and the reviewed combination rule. An additive bound may be used only when documented by that review. Astronomical tide alone does not establish total water-level certainty or currents.

The engine applies `lower = nominalMin - uncertainty` and `upper = nominalMax + uncertainty` once. Test-only 0.6–1.2 m nominal with 0.1 m uncertainty yields 0.5–1.3 m effective, not 0.4–1.4. Chart depth 5–7 m gives 5.5–8.3 m water depth; test-only draft 1.5 m gives 4.0 m clearance, and test-only bow 1 m/ratio 7 gives `ceil(9.3*7)=66 m` rode. These are analytical tests, not published guidance.
